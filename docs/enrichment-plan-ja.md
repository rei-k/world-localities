# 公式名称・郵便番号の追加設計

先に出典付きの基礎地名台帳を保存し、同じ地域IDに公式資料の情報を段階的に追加します。
この文書は実装・収集方針であり、公式データの収録完了を示すものではありません。
現在のアジア基礎台帳は52国・地域、3,277,921行です。公式名称辞書と郵便番号の全面的な紐付けは未完了です。

## 追加の順序

1. **基礎版の固定**: 国別データ、`gn:` ID、親子関係、出典、取得日時、ハッシュと未解決事項を保持する。
2. **公式地域コードとの対応**: 公的な自治体・行政区画IDと基礎IDの対応を出典付きで検証する。
   同名だけで結合しない。コード、所属階層、対象の種類、基準時点を照合する。
   自治体政府、行政区域、集落など異なる対象の関係は `same_as` と断定せず明示する。
3. **公式の言語別名称**: 当該機関が示す現地語・英語を別々の名称レコードとして追加する。
   言語、文字体系、国内/国際の用途、正式/慣用/旧称/転写の区別、出典と有効期間を保持する。
4. **郵便番号の対応**: 郵便事業者等の資料を取り込み、コードと地域を多対多で結ぶ。
   番号そのもの、配達区域、行政区域が一致するとは仮定しない。対応範囲と根拠を記録する。
5. **表示と検索の接続**: WorldAddressで地域IDから名称を選び、国・言語・用途別テンプレートに住所要素を配置する。
   国別に実例を検証し、確認した範囲を公開する。

## 地域IDは固定する

言語切り替えで地域IDそのものは入れ替えません。
同一IDについて、要求された言語・用途・基準日に合う名称を選択します。
地域の合併・分割や異なる対象への対応は別問題であり、履歴関係と有効期間を持つ対応表で表現します。
公式コードは `authority + scheme + code` の名前空間で管理し、原典の先頭ゼロを保持します。
欧州とアジアの重複収録は同じ `gn:` IDで照合し、異なる取得版の値を無条件で上書きしません。

## 追加する論理表

| 表 | 主な項目 | 役割 |
|---|---|---|
| entities | id、kind、country、parent_id、source_version | 地域の識別と所属 |
| identifier_links | entity_id、authority、scheme、code、relation、valid_from/to、evidence | 公式コードとの対応と根拠 |
| names | entity_id、language、script、audience、value、name_status、source_id、valid_from/to | 名称を翻訳済み住所全文と分離 |
| postal_links | entity_id、country、scheme、postal_code、granularity、coverage_relation、valid_from/to、source_id | 郵便番号との多対多の対応 |
| sources | source_id、publisher、URL、version、retrieved_at、license、sha256 | 原典と利用条件 |
| coverage | country、source_version、dimension、covered_count、denominator、status | 検証済み範囲・不足・母数 |
| address_templates | country、language、audience、fields、separator、source_id | WorldAddress側の表示順序 |

この表は追加仕様です。空の表や未収録の値を、公式に確認済みの地名・郵便番号として扱いません。
紐付け候補には `candidate/verified/rejected` の状態を持たせます。
同じ根拠のない複数候補は自動選択せず、未解決として残します。

## 言語と英語の扱い

国を単一言語/多言語の二値だけで処理せず、地域ごとの言語要件を設定します。
「国際英語」は用途、`en`・`en-IN`などは言語タグとして別項目にします。
国内用と国際用の英語表記が同一なら、名称を共有し、適用できる用途を記録します。
公式資料に国内用の英語があると確認できない場合は、新しい公式名称を生成しません。

名称選択の既定方針は、指定言語・用途の確認済み名称、同じ言語で共用できる確認済み名称の順です。
見つからなければ、明示的なフォールバック方針に従って別言語や転写を返し、
実際の言語、出典、`fallback_used`、生成方法を呼び出し側に伝えます。
要求が「公式英語のみ」であれば、未確認のローマ字表記を返して満たしたことにしません。
GeoNamesの `asciiname` は英語対訳の保証ではなく、`alternatenames` はこの基礎版では言語未特定です。

住所は、同じIDを基点に必要な名称を取得し、意味ごとの住所要素をテンプレートで並べます。
文字列全体の単純な逆順処理では、番地・建物名・郵便番号の位置を正しく扱えません。
この分離で国ごとの重複コードを減らせますが、公式名称・郵便番号対応の原典収集は別途必要です。

## 郵便番号と品質

郵便番号は文字列として保存します。完全な番号と接頭辞を `granularity` で区別し、
国・郵便制度を含めて識別します。1自治体に複数番号、1番号に複数地域の対応を表現できます。
郵便番号が一致することや代表座標が近いことだけで同一地域と確定しません。
同じ番号でも基準時点・事業者・用途によって対応が異なる場合は、別の出典付きレコードを保持します。

内部ハッシュ検証、公式地域との同一性、公式名称の言語確認、郵便対応の確認を別々に判定します。
国ごとに利用条件、原典の公開範囲、基準日、完全番号/接頭辞、未対応数を示します。
「全面対応」は母数と検証した対象範囲を定義して初めて判定し、資料未公開・確認未完了を区別します。

郵便番号制度がないと公式資料で確認できた対象は `not_applicable`、資料未公開は `unavailable`、
未照合は `pending` とし、未確認の対象を対応済みと数えません。
